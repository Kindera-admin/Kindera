# Kindera

Kindera connects corporate volunteers with NGO partners. Companies sign up their teams, NGOs and Kindera staff post volunteering events, volunteers register and log hours, and admins track impact across all of it.

Built with Next.js 15 (App Router), React 19, MongoDB (Mongoose), Tailwind CSS 4, shadcn/ui and Cloudinary. It is deployed on Vercel.

## Roles

| Role | Who | Lands on |
|------|-----|----------|
| `admin` | Kindera administrators | `/admin` (Control Centre) |
| `employee` | Kindera staff, who can also create NGO logins | `/admin` |
| `ngo` | NGO representatives, who submit monthly reports and upload 12A/80G/FCRA documents | `/dashboard` |
| `org_spoc` | Corporate single point of contact. Registered by an admin against a Company. All SPOCs of a company share its dashboard. | `/dashboard` |
| `org_member` | Corporate employees (`org_member`) of a company, with logins generated by any of its SPOCs or an admin | `/dashboard` |
| `volunteer` | Individual volunteers | `/dashboard` |

New accounts start as `pending` and wait on `/pending` until an admin approves them.

Corporate clients are `Company` records. Admins and Kindera staff (`employee`) create and manage them at `/admin/companies`. SPOCs and corporate employees (`org_member`) reference one through `companyId`. Public signup is for volunteers and NGOs only.

## Getting started

Requirements: Node.js 20+ and a MongoDB Atlas cluster (or any MongoDB URI).

```bash
npm install
cp .env.example .env.local   # then fill in the values
npm run create-admin         # creates the admin from ADMIN_* in .env.local
npm run dev                  # http://localhost:3000
```

### Environment variables

Each variable is described in [`.env.example`](.env.example). All env files except the example are gitignored.

| File | Used for | Database |
|------|----------|----------|
| `.env.local` | `npm run dev` / `npm run start` on your machine, and staging (`test` branch): import it in Vercel via `kindera-ngo` → Settings → Environment Variables → **Import .env**, environment **Preview**, branch **test** | Test cluster |
| *(Vercel only)* | kindera.co (`main`). Set under the **Production** environment in Vercel; there is no local copy | Production cluster |

| Variable | Used by |
|----------|---------|
| `MONGODB_URI` | `src/lib/db.js`, all scripts |
| `JWT_SECRET` | Signs and verifies the `auth-token` cookie (`src/lib/auth.js`, `src/middleware.js`) |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_NAME` | `npm run create-admin` |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | Cloudinary uploads |

## Scripts

| Command | What it does |
|---------|--------------|
| `npm run dev` / `build` / `start` / `lint` | Standard Next.js commands |
| `npm test` | Runs the Vitest suite against an in-memory MongoDB (no real database needed) |
| `npm run migrate:companies` | Moves free-text organisation names onto Company records. Dry run by default; `--apply --yes` applies, `--cleanup --yes` removes the old fields, `--rollback <file> --yes` restores the migration fields from a backup, `--backfill-legacy --yes` writes the old fields back before redeploying old code, `--env <file>` picks the env file. See "Company migration" below |
| `npm run seed:qa` / `npm run seed:qa -- --remove` | Creates or deletes prefixed QA accounts and companies. Refuses any database except the test cluster |
| `npm run create-admin` | Creates an admin user from `ADMIN_*` env vars and skips it if the user already exists |
| `npm run seed-events` | Inserts 5 sample events, only into an empty `events` collection |
| `npm run fix-index` | Rebuilds `users.ngoId_1` as a sparse unique index |
| `npm run check-data` | Prints the user count |
| `node scripts/clear-data.mjs` | **Destructive.** Wipes events, attendance, reports, messages, announcements and every non-admin, non-NGO user in the database that `MONGODB_URI` points at |

Scripts read `.env.local`, except `migrate-companies`, which reads the file given with `--env` (default `.env.local`), and `seed-qa`, which refuses any database other than the test cluster. Never hardcode a connection string in a script.

### Company migration

Run on the test database first, then production. Every write needs `--yes`.

1. Dry run: `npm run migrate:companies -- --env <file>`. Review the proposed companies, each company's SPOCs by status, and the unlinkable users and events (fix those first).
2. `--apply --yes`.
3. Deploy the new code.
4. `--apply --yes` again, immediately, to link records the old code wrote while the deploy was going out.
5. Verify.
6. `--cleanup --yes` after a few days without issues.

Rollback before cleanup:

1. `--backfill-legacy --yes`.
2. Redeploy the previous `main`.
3. `--backfill-legacy --yes` again, right after the old code is live, for records the new code wrote while the redeploy was going out.
4. Roll back every apply backup, newest first (`--rollback <apply backup> --yes` for each), or skip this step: `companyId` does no harm to the old code. A company that newer records still use is kept and reported.

Rollback after cleanup:

1. `--rollback <cleanup backup> --yes`.
2. `--backfill-legacy --yes`.
3. Redeploy the old code.
4. `--backfill-legacy --yes` again, right after the old code is live.

`--backfill-legacy` exits non-zero when records point at a company that no longer exists. It still writes an `Unknown company (<id>)` placeholder on them so the old code keeps them private. Restore those companies or re-link the records, then run it again: it replaces the placeholders and exits cleanly once none remain. `--cleanup` refuses while any such record exists.

## Project structure

```
src/
├── app/
│   ├── actions.js          # nearly all server logic ("use server" actions)
│   ├── admin/              # admin and employee Control Centre pages
│   ├── dashboard/          # NGO, corporate and volunteer dashboards
│   ├── events/             # event list, creation and registration
│   ├── reports/            # NGO monthly reports
│   ├── messages/           # direct messaging
│   ├── partners/           # public NGO partners page
│   └── api/                # upload route only (everything else is a server action)
├── components/             # shared components; shadcn/ui primitives in components/ui
├── lib/                    # db connection, auth helpers, utils
├── models/                 # Mongoose models (User, Event, Attendance, Report, …)
└── middleware.js           # cookie auth and role gate for page routes
scripts/                    # one-off maintenance scripts (see above)
docs/FEATURES.md            # detailed feature notes
```

Pages use the same pattern throughout. `page.js` is a server component that fetches data through `actions.js` and renders a `*Client.js` client component, and `loading.js` supplies a skeleton.

## Deployment

Two long-lived branches in `Kindera-admin/Kindera`:

| Branch | Deploys to | Database |
|--------|-----------|----------|
| `main` | **https://kindera.co** (live, Vercel project `kindera-ngo`) | Production MongoDB cluster |
| `test` | **Staging** (test site) | Test cluster |

Workflow:

1. Do all work on `test` (or a feature branch merged into `test`) and check it on staging.
2. When staging looks right, merge `test` into `main` to release to kindera.co.
3. Never push straight to `main`.

Local `.env.local` should always point at the **test** cluster, never production. Run `npm run build` before you push.
